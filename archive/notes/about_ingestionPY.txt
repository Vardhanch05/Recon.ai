File Summary (One-Paragraph Note)
backend/ingestion.py is the data parsing, validation, and normalization service for the reconciliation backend. 
It processes raw multipart CSV file bytes from payment gateways (settlement payout reports) and merchant carts (order ledgers), 
sanitizing irregular currency formatting (e.g. ₹ symbols, commas) and varying timestamp formats. Crucially, it implements row-level error isolation: if a corrupt row is encountered, 
it logs a detailed ingestion_error event to the immutable audit_log and continues processing remaining transactions without crashing the upload batch.


🔑 Key Concepts, Types & Functions Used

1. clean_currency(val)
   Strips currency symbols (₹, $, €), thousands separators (,), and whitespace, safely converting messy financial strings to exact Python floats.

2. parse_datetime(val)
   Iterates through 7 common date-time formatting schemas (ISO 8601, European, US, standard SQL timestamps) to reliably parse transaction times across disparate gateway files.

3. parse_csv_stream(file_bytes)
   Decodes raw file bytes using utf-8-sig to automatically strip Excel Byte Order Marks (\ufeff) and trims leading/trailing whitespace from CSV headers and cells.

4. Row-Level Error Isolation (try/except inside row loop)
   Prevents one corrupt line in a 10,000-row file from failing the entire batch. Malformed rows write an ingestion_error event to audit_log with row index and raw JSON payload.

5. db.flush() vs db.commit()
The core difference is that db.flush() synchronizes in-memory changes with the database transaction buffer without making them permanent, 
while db.commit() makes those changes permanent and ends the transaction

💡 Explainability Tip for Interviews / Project Reviews
If asked: "How does your backend handle dirty CSV data and partial ingestion failures?"
Your answer:
"In ingestion.py, we sanitize incoming data using robust currency and multi-format datetime parsers with UTF-8-BOM decoding. 
To prevent entire batch failures due to a few bad rows, we employ a 
row-level error isolation pattern: valid rows are staged for database persistence, while any malformed row is caught, skipped, and logged as an ingestion_error event in our immutable audit_log for audit review."
